> [!sheet] 판서 「탄광의 카나리아」 · 7강
> **다른 층, 다른 추상**

> [!abstract] 이 강에서
> 잘 설계된 시스템에서는 층마다 위아래와 다른 추상화를 제공해야 한다는 원칙을 세우고, 이를 어기는 모양 넷인 통과 메서드, 얕은 데코레이터, 구현을 그대로 드러낸 인터페이스, 통과 변수를 차례로 진단한다. 통과 변수의 해법으로 불변의 문맥 객체를 권하되 그 한계를 인정하고, 고 언어의 context.Context와 견준다.

원서7장 Different Layer, Different Abstraction · 7.1 통과 메서드 · 7.2 [[인터페이스]] 중복이 괜찮을 때 · 7.3 데코레이터 · 7.4 인터페이스 대 구현 · 7.5 통과 변수 · 7.6 결론

지난 시간 끝에 모래시계를 그렸지요. 위아래 끝에 특수한 것, 가운데 허리에 범용. 그러니까 소프트웨어가 층으로 쌓여 있다는 그림이었습니다. 오늘은 그 층들 *사이*의 규칙이에요.

여는 질문. 층을 하나 더 쌓으면 왜 오히려 나빠질 수 있습니까? 이건 [[추상화]] 층이 많을수록 좋을 것 같지만은, 한 번 진지하게 생각해 보면 그렇지가 않아요. 통역사를 한 명 두면 말이 통하지요. 그런데 한국어를 한국어로 통역하는 통역사를 한 명 더 두면요? 말이 한 번 더 전달될 뿐 아무것도 보태지지 않고, 오히려 그 사람이 말을 잘못 옮길 기회가 하나 늘어요. 층은 *다른 말*로 바꿔 줄 때만 값을 합니다.

이 양반의 주장이 딱 그거예요. 잘 설계된 시스템에서는 [[층이 다르면 추상화도 달라야 한다|각 층이 그 위아래 층과]] *다른*추상화를 제공한다. 예가 파일 시스템이에요. 맨 위 층은 파일을, 길이가 가변인 바이트 배열로 보여 줍니다. 아무 위치에서 아무 길이로 읽고 쓸 수 있는 연속된 바이트들. 그 아래 층은 메모리 속의 캐시로, 고정 크기 디스크 블록들을 관리해요. 맨 아래 층은 장치 드라이버로, 블록을 저장 장치와 메모리 사이에서 옮깁니다. 층마다 세상을 보는 단위가 달라요. 바이트 배열, 블록 캐시, 장치 명령. 네트워크의 [[TCP]]도 같아요. 위에서는 믿을 수 있는 바이트 스트림을 보여 주는데, 그 아래는 잃어버리거나 순서가 뒤바뀔 수 있는 크기 제한된 패킷들을 최선을 다해 배달하는 층이지요. 신뢰할 수 없는 것 위에 신뢰를 세우는 층이니, 확실히 다른 추상화입니다. 그리고 이 양반의 경고. 인접한 두 층이 비슷한 추상화를 갖고 있다면, 그건 클래스 분해에 문제가 있다는 [[레드 플래그|경고 신호]]다. 이 장은 그 경고 신호가 겉으로 드러나는 모양 넷을 차례로 봅니다.

7.1절, [[통과 메서드|통과 메서드pass-through method]]. 하는 일이라곤 시그니처가 비슷하거나 똑같은 다른 메서드를 부르는 것뿐인 메서드. [[편집기 텍스트 클래스|학생 편집기 프로젝트]]에서 나온 예를 드는데, 문서를 나타내는 클래스가 속에 텍스트 영역 객체를 하나 들고 있고, 문서 클래스의 메서드들이 대부분 그 텍스트 영역의 같은 이름 메서드를 그대로 부르고 있었어요. 두 중국어 번역본이 똑같이 옮긴 대목에 따르면 [[통과 메서드 열다섯 중 열셋|공개 메서드 열다섯 개 가운데 열세 개가 통과 메서드]]였다고 합니다. 영문 원문은 제가 직접 확인하지 못했어요. 모양을 새로 써 보면 이런 식이지요.

```
public class Doc {
    private TextPane pane;
    public int caretIndex()             { return pane.caretIndex(); }
    public char lastTyped()             { return pane.lastTyped(); }
    public void insert(String s, int i) { pane.insert(s, i); }
}
```

한 줄씩 봅시다. 첫 줄, 문서 클래스예요. 둘째 줄, 이 클래스가 화면의 텍스트 영역 객체를 하나 들고 있어요. 셋째 줄, 커서 위치를 물으면 텍스트 영역에 똑같이 물어서 그 답을 그대로 돌려줍니다. 넷째 줄, 마지막으로 친 글자도 똑같이. 다섯째 줄, 글자를 끼워 넣으라 하면 인자를 그대로 넘겨요. 세 메서드 다 몸통이 한 줄이고, 이름도 인자도 넘기는 쪽과 같습니다.

> [!calc] 손계산통과 메서드의 비율
> 1. 공개 메서드 15개 중 통과 메서드 13개 → 13 ÷ 15 ≈ 86.7%
> 2. 이 클래스 인터페이스의 87%는 다른 클래스 인터페이스의 복사본이고, 이 클래스만의 기능을 담은 메서드는 2개입니다. [[소프트웨어설계 04강 모듈은 깊어야 한다|4강]]의 사각형으로 말하면 위쪽 변의 13/15가 넓이를 한 칸도 보태지 않습니다.

무엇이 나쁘냐. 첫째, [[얕은 모듈|클래스가 얕아져요]]. 인터페이스는 늘었는데 기능은 그대로니까. 둘째, 의존이 생깁니다. 텍스트 영역의 `insert` 시그니처가 바뀌면 문서 클래스의 `insert`도 바뀌어야 해요. 한 결정이 두 곳에 새는 겁니다. 셋째, 책임이 흐려져요. 커서 위치는 누가 책임지오? 문서요, 텍스트 영역이오? 둘 다 대답을 하니 알 수가 없지요.

> [!danger] 레드 플래그 통과 메서드(Pass-Through Method).
> 인자를 거의 그대로 다른 메서드에 넘기는 것 말고는 하는 일이 없는 메서드. 흔히 같은 API를 가진 메서드로 넘긴다. 클래스들 사이의 책임 분담이 깨끗하지 않다는 뜻이다.

처방은 넷 가운데서 고릅니다. 이 양반이 그림으로 보여 주는데, 원래 상태는 윗 클래스가 통과 메서드로 아랫 클래스를 부르는 거예요. 첫째 처방, 윗 클래스를 부르던 쪽이 아랫 클래스를 *직접*부르게 한다. 둘째, 기능을 다시 나눠서 애초에 넘길 필요가 없게 한다. 셋째, 두 클래스를 합친다. 학생들은 둘째 길로 가서 책임을 다시 나누었고, 문서·텍스트 영역·리스너 세 클래스를 두 클래스로 줄였다고 해요.

7.2절, 인터페이스 중복이 괜찮을 때. 여기서 이 양반이 곧바로 브레이크를 밟습니다. 시그니처가 같은 메서드가 여럿 있는 것 자체는 괜찮다. 중요한 건 각 메서드가 *의미 있는 기능*을 보태느냐다. 예가 둘이에요. 하나는 [[디스패처]]. 웹 서버가 HTTP 요청을 받으면, 디스패처가 URL을 보고 어느 처리기에 보낼지를 고르지요. 정적 파일을 돌려주는 처리기, [[스크립트]]를 돌리는 처리기. 디스패처의 시그니처는 처리기들과 같을 수 있어요. 요청을 받아 응답을 내는 거니까. 그런데 디스패처는 *고르는*일을 합니다. 그게 기능이에요. 다른 하나는 같은 인터페이스의 여러 구현. 운영체제의 [[장치 드라이버|디스크 드라이버]]들은 디스크 종류마다 따로 있지만 같은 인터페이스를 가지지요. 지난 시간의 모래시계 아래 끝이에요. 이건 오히려 [[인지 부하]]를 *줄입니다*. 드라이버 하나를 알면 나머지도 어떻게 쓰는지 알거든요. 그리고 이 메서드들은 같은 층에 나란히 있을 뿐 서로를 부르지 않아요. 층을 가로지르는 복사가 아니라 층 안의 형제들이지요.

7.3절, [[데코레이터|데코레이터decorator]]. 래퍼wrapper라고도 하지요. 기존 객체를 받아서, 같거나 비슷한 API를 제공하면서 기능을 조금 덧붙이는 객체. 4강의 [[자바 입출력 클래스|자바 입출력]]에서 본 `BufferedInputStream`이 대표예요. 다른 입력 스트림을 감싸서 같은 API를 주되, 밑에서 큰 덩어리로 읽어 두고 위에는 조금씩 내주는 버퍼링을 덧붙이지요. 창 객체를 감싸서 가로세로 스크롤 막대를 붙이는 스크롤 창도 예로 들고요. 데코레이터를 쓰는 동기는 좋아요. 특수한 확장을 범용 핵심에서 떼어 놓자는 것, 지난 시간의 교훈 그대로입니다. 그런데 이 양반은 데코레이터가 얕아지기 쉽다고 경고해요. 조금의 새 기능을 위해 판박이 코드와 통과 메서드를 잔뜩 들이게 되니까요. 감싸는 객체는 감싸인 객체의 메서드를 전부, 대개는 그대로 다시 제공해야 하거든요. 그래서 새 기능 하나마다 데코레이터 하나를 만드는 식으로 남용하기가 쉽다.

데코레이터를 만들기 전에 따져 볼 대안을 넷 줍니다. 하나, 그 기능이 범용적이거나 밑바탕 클래스와 논리적으로 이어지거나 대부분의 사용자가 원한다면, 밑바탕 클래스에 직접 넣어라. 입력 스트림을 만드는 사람은 거의 모두 버퍼링 스트림도 만드니까, 버퍼링은 처음부터 안에 있어야 했지요. 둘, 그 기능이 특정한 쓰임에만 필요하다면 데코레이터가 아니라 그 쓰임 쪽 코드에 합쳐라. 셋, 이미 있는 데코레이터와 합쳐서 더 깊은 데코레이터 하나로 만들어라. 넷, 감싸지 말고 독립된 클래스로 구현할 수 있는지 보라. 스크롤 막대가 꼭 창 전체를 감쌀 필요가 있는지. 그러면서도 바꿀 수 없는 외부 클래스를 내 시스템에 맞추는 경우처럼 래퍼가 정당한 때가 있다는 것도 인정합니다.

7.4절, 인터페이스 대 구현. 이 장의 원칙을 한 클래스 안으로 가져오면 이렇게 됩니다. [[클래스의 인터페이스는 구현과 달라야 한다|클래스의 인터페이스는 대개 그 구현과]] *달라야*한다. 속에서 쓰는 표현을 겉으로 그대로 내보이면 클래스는 얕아져요. 또 편집기 예가 나와요. 학생들은 대부분 텍스트를 속에서 줄 단위로 저장했습니다. 그건 괜찮아요. 문제는 일부 팀이 인터페이스까지 줄 단위로 만든 것이었지요. 몇 번째 줄을 가져오기, 몇 번째 줄을 바꿔 넣기. 그러자 화면 쪽이 줄 사이에서 글자를 넣거나 여러 줄에 걸친 범위를 지울 때마다 줄을 쪼개고 붙이는 일을 직접 해야 했어요. 줄바꿈 한 번 치는 게 “이 줄을 둘로 쪼개라”가 되니까요. 대안은 지난 시간의 글자 단위 `insert`와 `delete`를 인터페이스로 내놓고, 줄은 속에서만 쓰는 겁니다. 그러면 줄을 쪼개고 붙이는 [[복잡성]]이 텍스트 클래스 *안에*갇히고 클래스는 깊어져요. 이 예는 다음 강에서 “복잡성을 아래로” 끌어내리는 이야기로 한 번 더 쓰입니다.

7.5절, [[통과 변수|통과 변수pass-through variable]]. 메서드뿐 아니라 변수도 층을 그냥 지나갈 수 있어요. 긴 메서드 호출 사슬을 따라 아래로 내려 보내지기만 하고, 중간 메서드들은 쓰지도 않는 변수. 이 양반 예가 이래요. 데이터센터 서비스 하나가 명령행에서 보안 통신에 쓸 인증서 정보를 받아요. 그 정보가 실제로 필요한 곳은 저 밑의 메서드 하나, 네트워크 소켓을 여는 라이브러리를 부르는 곳이에요. 그런데 거기까지 가려면 `main`에서 받은 인증서를 첫째 메서드에, 첫째가 둘째에, 둘째가 셋째에 인자로 넘겨야 하지요. 중간의 두 메서드는 인증서를 쓰지도 않는데 시그니처에 인증서가 들어가 있어요. 모든 중간 메서드가 인증서의 존재를 알게 된 겁니다. 게다가 나중에 이런 변수가 하나 더 생기면, 예컨대 처음엔 인증서를 안 썼는데 나중에 보안 통신을 붙이게 되면, 사슬 위의 시그니처를 전부 고쳐야 해요.

> [!calc] 손계산통과 변수 하나를 새로 들일 때 고쳐야 하는 곳
> 1. 호출 사슬 main → a → b → c 에서 c만 새 변수를 쓴다고 합시다.
> 2. 시그니처를 고칠 메서드: a, b, c = 3개. 그 메서드들을 부르는 곳: main→a, a→b, b→c = 3곳.
> 3. 그런데 a가 b를 두 곳에서, b가 c를 세 곳에서 부른다면 호출 지점은 1 + 2 + 3 = 6곳이 됩니다.
> 4. 쓰는 곳은 1곳인데 고치는 곳은 3 + 6 = 9곳. 사슬이 깊고 가지가 많을수록 이 비율이 곱으로 커집니다. [[소프트웨어설계 02강 복잡성의 본성|2강]]의 [[변경 증폭]]이 호출 그래프를 따라 번지는 모양입니다.

처방을 셋 검토해요. 첫째, `main`과 맨 밑 메서드가 둘 다 이미 참조하고 있는 공유 객체가 있으면 거기에 담는다. 그런데 이 양반이 곧바로 묻지요. 그 맨 밑 메서드는 그 공유 객체를 어떻게 참조하게 됐을까요? 그 객체 자체가 통과 변수로 내려왔을지도 모릅니다. 둘째, 전역 변수. 이건 한 프로세스 안에서 시스템의 독립된 인스턴스를 둘 띄울 수 없게 만들어요. 둘이 같은 전역을 건드리니까. 실제 운영에서는 드문 일이지만 시험할 때는 유용한데 그게 막히지요. 셋째, 이 양반이 가장 자주 쓴다는 해법, [[문맥 객체|문맥 객체context object]]예요.

문맥 객체는 시스템 인스턴스 하나마다 하나씩 두는, 응용의 전역 상태를 담는 객체입니다. [[설정 매개변수|설정 값]]들, 타임아웃 같은 것, 여럿이 함께 쓰는 하위 시스템들, 성능 카운터, 그리고 인증서. 시스템의 주요 객체들은 대부분 이 문맥 객체를 가리키는 참조를 들고 있어요. 모양을 새로 써 보면 이렇습니다.

```
final class Ctx {
    final Certificate cert;
    final Duration rpcTimeout;
    Ctx(Certificate c, Duration t) { cert = c; rpcTimeout = t; }
}
class Session {
    private final Ctx ctx;
    Session(Ctx ctx) { this.ctx = ctx; }
    Channel open() { return Tls.connect(host, ctx.cert); }
    Reader newReader() { return new Reader(ctx); }
}
```

한 줄씩 봅시다. 첫 줄, 문맥 클래스. 둘째와 셋째 줄, 인증서와 RPC 타임아웃을 담는데 둘 다 `final`, 곧 한 번 정하면 못 바꿉니다. 이게 뒤에서 중요해요. 넷째 줄, 생성자에서 한 번에 채웁니다. 여섯째 줄부터 문맥을 쓰는 쪽이에요. `Session` 객체가 문맥을 참조로 들고 있고, 여덟째 줄의 생성자에서 받습니다. 아홉째 줄, 상대 서버(`host`, 이 세션이 따로 들고 있는 주소라 칩시다)로 소켓을 열 때 문맥에서 인증서를 꺼내 써요. 인증서가 인자로 내려오지 않았지요. 열째 줄이 이 설계의 요령인데, `Session`이 새 객체 `Reader`를 만들 때 자기가 든 문맥 참조를 새 객체의 생성자에 넘겨줍니다. 그래서 문맥이 명시적으로 등장하는 곳은 *생성자*뿐이고, 일반 메서드의 시그니처에는 안 나타나요.

이득은 셋이에요. 새 전역 값이 생기면 문맥에 필드 하나만 보태면 되고, 시스템의 전역 상태가 한 곳에 모여 있고, 시험할 때 문맥의 필드를 바꿔 끼워 설정을 쉽게 바꿀 수 있다. 그런데 이 양반은 정직하게 한계를 인정합니다. 문맥은 이상적인 해법과는 거리가 멀다. 전역 변수의 단점을 대부분 그대로 가진다. 왜 이 필드가 여기 있는지, 어디서 쓰이는지가 뻔하지 않을 수 있고, 관리하지 않으면 온갖 데이터를 쓸어 담는 잡동사니 자루가 된다. 여러 스레드가 함께 쓰면 동기화 문제가 생기는데, 이건 문맥의 변수를 바꿀 수 없게, 불변으로 만드는 게 가장 좋다. 제 예시에서 `final`을 붙인 게 그래서예요. 그리고 이 양반의 고백. 불행히도 나는 문맥보다 나은 해법을 찾지 못했다.

곁가지 하나. 이 문맥 객체가 오늘날 가장 널리 퍼진 모습이 [[context.Context (Go)|고 언어]]의 `context.Context`예요. 2014년에 실험 패키지로 나왔다가 2016년 고 1.7에서 표준 라이브러리에 들어갔지요. 그런데 흥미롭게도 고는 문맥을 객체의 필드로 들고 다니지 *말고*모든 함수의 첫 번째 인자로 명시적으로 넘기라는 관례를 택했어요. 취소 신호와 마감 시각이 호출마다 다르니까요. [[존 오스터하웃|오스터하우트]] 식으로 말하면, 고는 통과 변수를 일부러 받아들이고 대신 그걸 *모두가 알아보는 단 하나의 관례*로 만든 셈이에요. 통과 변수의 해악이 “중간 메서드마다 새로 알아야 할 것이 생긴다”는 데 있다면, 모든 함수에 똑같은 모양으로 붙는 인자는 새로 알아야 할 게 하나뿐이지요. [[소프트웨어설계 17강 일관성|17강]]의 [[일관성]]이 통과 변수의 비용을 깎아 준 경우라 볼 수 있습니다.

7.6절 결론. [[설계 요소는 보태는 것보다 많은 복잡성을 없애야 한다|시스템에 보태는 모든 설계 기반 요소]], 인터페이스든 인자든 함수든 클래스든 정의든, 그것 하나하나가 복잡성을 보탠다. 개발자가 그걸 배워야 하니까. 그러니 그 요소가 *없애는*복잡성이 보태는 복잡성보다 커야 한다. 같은 추상화를 [[코드 되풀이|되풀이]]하는 층들, 통과 메서드와 얕은 데코레이터, 그리고 통과 변수는 대개 자기 값을 하지 못한다.

> [!claim] 설계 원칙
> - 층이 다르면 추상화도 달라야 한다.

오늘을 묶지요. 층은 다른 말로 바꿔 줄 때만 값을 한다. 같은 말을 되풀이하는 층은 통역사 없는 통역이다. 메서드가 그냥 지나가면 통과 메서드, 변수가 그냥 지나가면 통과 변수. 그리고 불가피한 전역 상태는 불변의 문맥 하나에 모은다. 다음 시간에는 층 사이에서 복잡성을 *어느 쪽으로*밀어야 하느냐, 위냐 아래냐를 봅니다.
